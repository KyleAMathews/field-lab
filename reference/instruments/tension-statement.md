# Tension statement (`tension-statement`)

- **Phenomenon sought:** Whether a live contradiction exists, and whether a current tension remains live, sharpens, moves, thins out, or dissolves as inquiry proceeds.
- **Why use it:** A list of complaints does not show which demands collide under which condition. A single compression can smuggle in the orchestrator's favorite frame, while a one-time selection can make a provisional direction feel fixed. A traced menu and cheap later rechecks keep the user free to follow what the inquiry reveals.
- **Operating range:** Two or more sound demands that cannot all hold under current conditions. Do not force a dialectic when evidence favors one side.
- **Input:** For an initial pass, the claims, stakes, and candidate collision conditions. For a recheck, the current tension, prior menu or trail, and the user corrections or new material since the last check.
- **Perturbation:** Compresses a messy field into candidate structures and later compares one structure against new material. Either move can create salience or apparent instability that was not present before.
- **Procedure:**
  1. Make a short provenance inventory before drafting: user statements and corrections, other supplied conversation or artifacts, outside source claims, and orchestrator inferences. Keep those kinds distinct.
  2. **Initial pass:** Test whether the inventory supports at least two sound demands that collide under a concrete condition. If not, return **no supported tension found**, name what is missing, and stop. Otherwise generate a burst of 5–8 structurally different candidates, including one close to the user's terms. Cluster them into 2–4 unranked working options.
  3. For each initial option, state: “We need or value **A**, and we also need or value **B**, but under **C**, doing A undermines B because **mechanism**.” Add brief **roots** (what the user said or supplied), **new move** (outside source or inference, if any), **what would weaken it**, and **what this framing may leave out**.
  4. **Recheck:** First reread the whole inquiry: original question, stated goal, full interview and corrections, accumulated sources, current tension, and prior trail. Then compare the user corrections and new material since the last check against that gestalt. Mark each new item `supports`, `sharpens`, `side trail`, `weakens`, or `decisive dissolve`; do not let recency or vivid wording set the frame.
  5. Classify the current version:
     - `live` — both demands, the collision condition, and the mechanism still have support;
     - `sharpened` — the same basic collision survives but a demand, condition, or mechanism is now more precise;
     - `moved` — the live conflict now requires different demands, a different condition, or a different mechanism;
     - `thin` — one pole or the claimed mechanism no longer carries enough support for committed opposition;
     - `dissolved` — a new distinction or fact removes the collision.
  6. Require a movement threshold. Mark `moved` only when the new material changes a load-bearing demand, condition, or mechanism, still matters to the user's stated goal when read against the whole record, and is supported beyond its own novelty—by recurrence, other material, or the user's confirmation that it is central. A single item may still yield `dissolved` when it directly defeats the collision. Otherwise keep the current tension and park the item as a side trail.
  7. For `live` or `sharpened`, show the small delta and ask whether to continue, rewrite, or change direction; do not repeat the full burst by default. For `moved`, `thin`, or `dissolved`, bring back any still-supported parked options and generate only enough new candidates to present 2–4 unranked directions. Run a fresh 5–8 burst only when the existing trail no longer covers the field.
  8. Present every surviving option. Do not call one the real, deepest, strongest, or most fertile tension. Ask the user to continue, choose, combine, rewrite, park, or reject them all. Treat that response as user-fit, not proof that the tension is true. A choice is the current working direction, not a promise to keep it. If a selected workflow schedules a menu-level control before choice, keep this instrument `running`, apply that control, then present the final unranked menu; the user's response completes the reading.
- **Readout:** For an initial pass, either a supported **none found** result or the burst, 2–4 traced options, and the user's current selection. For a recheck, the prior and current versions, one status (`live`, `sharpened`, `moved`, `thin`, or `dissolved`), the exact new material that caused the status, any revised menu, and the user's current direction. Keep generated candidates, status, and user choice separate.
- **Control:** Restate the provenance inventory without a binary and see what disappears. Audit every load-bearing term and causal claim by source kind. On recheck, compare against both the last recorded version and the whole-inquiry gestalt. Ask whether apparent movement came from cumulative support, a decisive defeater, the user's changed aim, the orchestrator's wording, or mere recency.
- **Common artifacts:** The syntax manufactures symmetry or conflict; clustering hides a live alternative; source language gains false authority; a provisional choice hardens into a fixed frame; a vivid article or fresh thought hijacks the inquiry; ordinary clarification is mislabeled as movement; sunk-cost pressure keeps a thin tension alive.
- **Escalate when:** Both poles remain live after correction and the outcome matters.
- **Stop when:** No live collision is supported, or the current status, delta, user direction, and provenance are recorded.
- **What it requires:** A brief conversation and enough concrete examples to test the wording.
- **Execution placement:** **Orchestrator.** It needs the accumulated claims, stakes, and user corrections to produce and trace the burst. A fresh subagent may add candidates or challenge the menu but does not choose the working tension. If continuity is lost, restate the provenance inventory and ask the user to correct it before generating options.
